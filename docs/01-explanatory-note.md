# Пояснительная записка

## Тема проекта

**Автоматизация процесса создания документооборота промышленного предприятия.**

## 1. Введение

### 1.1. Актуальность

Промышленное предприятие генерирует большое число внутренних документов:
служебные записки, заявки на материалы и оборудование, приказы, акты приёмки и
списания, заявки на ремонт. Без специализированной системы документооборота
такие документы:

- ведутся в разрозненных Word/Excel-файлах,
- теряются при пересылке по почте,
- не имеют сквозной нумерации,
- не сохраняют историю согласования,
- сложно поддаются аудиту.

Автоматизация документооборота позволяет:

1. Стандартизировать форму всех типовых документов.
2. Гарантировать уникальную нумерацию и единое место хранения.
3. Реализовать прозрачные маршруты согласования.
4. Получить отчётность по статусам и срокам.
5. Соблюдать требования внутреннего аудита.

### 1.2. Цель работы

Разработать настольное приложение для автоматизации создания и согласования
типовых документов промышленного предприятия с возможностью локальной работы
без серверной инфраструктуры.

### 1.3. Задачи

- Спроектировать схему данных СЭД (Система Электронного Документооборота).
- Реализовать модуль авторизации с ролевой моделью.
- Реализовать конструктор документов на базе шаблонов.
- Реализовать произвольные последовательные маршруты согласования.
- Реализовать журнал, поиск, фильтры, экспорт.
- Подготовить документацию и инструкции.

## 2. Анализ предметной области

### 2.1. Типовые документы промышленного предприятия

| Документ                       | Кто создаёт            | Кто согласует/утверждает              |
| ------------------------------ | ---------------------- | ------------------------------------- |
| Служебная записка              | любой сотрудник        | руководитель адресата                 |
| Заявка на материалы            | сотрудник цеха         | начальник цеха → склад                |
| Приказ                         | руководитель / отдел кадров | директор                         |
| Акт                            | комиссия               | руководитель подразделения            |
| Заявка на ремонт оборудования  | сотрудник цеха         | начальник цеха → главный механик      |

### 2.2. Жизненный цикл документа

```
Черновик ──submit──> На согласовании ──approve* (все шаги)──> Утверждён ──execute──> Исполнен ──archive──> В архиве
                              │
                              └──reject──> Отклонён ──archive──> В архиве
```

### 2.3. Обзор аналогов

| Система              | Класс                  | Минусы для учебного/малого внедрения             |
| -------------------- | ---------------------- | ------------------------------------------------ |
| 1С:Документооборот   | Корпоративная СЭД      | Платная, тяжёлый клиент-сервер, требует 1С       |
| Directum / DirectumRX| Корпоративная СЭД      | Платная, серверная установка                     |
| ELMA365              | BPM / СЭД (облако)     | Облачная, абонентская плата                      |
| Alfresco             | OpenSource CMS         | Java-стек, требует JVM и СУБД                    |
| Nuxeo                | OpenSource ECM         | Java/Tomcat, серверная                           |

Все аналоги — серверные. Цель проекта — локальное **lightweight**-решение
без сервера, подходящее для лабораторной работы и небольшого подразделения.

## 3. Постановка задачи

### 3.1. Функциональные требования

- F1. Авторизация: вход по логину/паролю; роли `employee`, `manager`, `admin`.
- F2. Шаблоны документов: 5 предустановленных типов с настраиваемыми полями.
- F3. Создание документа из шаблона с автоподстановкой реквизитов автора и даты.
- F4. Назначение последовательного маршрута согласования (1+ согласующих).
- F5. Действия согласующего: согласовать (с комментарием) или отклонить
  (с обязательным комментарием).
- F6. После всех успешных шагов документ становится утверждённым; после отклонения
  оставшиеся шаги пропускаются.
- F7. Утверждённый документ можно отметить как исполненный.
- F8. Любой завершённый документ можно отправить в архив.
- F9. Поиск и фильтрация документов: по статусу, автору, тексту.
- F10. Дашборд: счётчики по статусам, документы на моём согласовании, просрочка.
- F11. Экспорт документа в PDF.
- F12. Журнал аудита всех действий (только администратор).
- F13. Управление пользователями (создание, активация — только администратор).

### 3.2. Нефункциональные требования

- NF1. Локальная работа без сервера и сети.
- NF2. Кроссплатформенность: Windows / Linux / macOS.
- NF3. Хранение паролей в виде bcrypt-хешей.
- NF4. Изоляция renderer-процесса (contextIsolation, без nodeIntegration).
- NF5. Поддержка кириллицы во всех модулях, включая PDF-экспорт.

## 4. Проектирование

### 4.1. Архитектура приложения

Приложение построено по двухпроцессной модели Electron:

```
┌──────────────────────────────────┐         ┌──────────────────────────────┐
│      Renderer process (UI)       │  IPC    │      Main process (Node.js)  │
│  React + Router + Zustand        │ ◄────►  │  Service layer (TS)          │
│  TailwindCSS                     │         │  ├─ auth                     │
│                                  │         │  ├─ documents                │
│  window.api.* (preload bridge)   │         │  ├─ users / templates        │
└──────────────────────────────────┘         │  ├─ pdf (pdfkit)             │
                                             │  └─ audit                    │
                                             │              │               │
                                             │              ▼               │
                                             │    better-sqlite3 (синхр.)   │
                                             │              │               │
                                             │              ▼               │
                                             │     doc-flow.sqlite (WAL)    │
                                             └──────────────────────────────┘
```

- **Main process** — Node.js, имеет доступ к ФС и БД, выполняет всю
  бизнес-логику.
- **Renderer process** — изолирован, не имеет прямого доступа к Node API;
  общается с main исключительно через `ipcRenderer.invoke`.
- **Preload script** — выставляет в `window.api` типизированные обёртки над
  IPC-каналами через `contextBridge.exposeInMainWorld`.

### 4.2. Схема базы данных (ER)

```
┌──────────────┐       ┌──────────────┐
│    users     │1     *│  documents   │
│──────────────│◄──────│──────────────│
│ id (PK)      │       │ id (PK)      │
│ username     │       │ number (UQ)  │       ┌────────────────┐
│ password_hash│       │ template_id  │──────►│   templates    │
│ full_name    │       │ title        │       │────────────────│
│ role         │       │ status       │       │ id (PK)        │
│ department   │       │ author_id    │       │ code (UQ)      │
│ position     │       │ data_json    │       │ title          │
│ is_active    │       │ body_rendered│       │ description    │
│ created_at   │       │ created_at   │       │ fields_json    │
└──────────────┘       │ updated_at   │       │ body_template  │
       ▲               └──────┬───────┘       │ created_at     │
       │                      │               └────────────────┘
       │                      │ 1
       │                      │
       │                      │ *
       │               ┌──────▼─────────┐
       │ approver_id   │ approval_steps │
       └───────────────│────────────────│
                       │ id (PK)        │
                       │ document_id    │
                       │ approver_id    │
                       │ step_order     │
                       │ status         │
                       │ comment        │
                       │ acted_at       │
                       └────────────────┘

┌─────────────┐
│  audit_log  │
│─────────────│
│ id (PK)     │
│ user_id     │ (FK → users)
│ action      │
│ entity_type │
│ entity_id   │
│ details     │
│ created_at  │
└─────────────┘
```

Все справочные коды и статусы реализованы через `CHECK`-ограничения SQLite,
индексы построены на полях, по которым ведётся фильтрация (`status`,
`author_id`, `approver_id + status`).

### 4.3. Шаблонизация документов

Шаблон описывается двумя полями:

1. `fields_json` — JSON-массив описаний полей формы:
   ```json
   [
     { "key": "addressee", "label": "Кому", "type": "text", "required": true },
     { "key": "body", "label": "Текст", "type": "textarea", "required": true }
   ]
   ```
2. `body_template` — текст с плейсхолдерами `{{key}}`, которые заменяются
   значениями из формы и автоподставляемыми реквизитами автора:
   - `{{number}}`, `{{created_date}}`
   - `{{author_name}}`, `{{author_position}}`, `{{author_department}}`

Поддерживаемые типы полей: `text`, `number`, `date`, `textarea`, `select`.

### 4.4. Алгоритм согласования

```python
def approve(document, current_user, comment):
    step = first_pending_step(document, by=current_user)
    step.status = 'approved'
    step.comment = comment
    step.acted_at = now()
    if no_more_pending_steps(document):
        document.status = 'approved'

def reject(document, current_user, comment):
    step = first_pending_step(document, by=current_user)
    step.status = 'rejected'
    step.comment = comment
    document.status = 'rejected'
    skip_remaining_pending_steps(document)
```

Все операции выполняются в транзакции SQLite, что гарантирует консистентность
статусов документа и шагов.

### 4.5. Безопасность

- **Хеш паролей** — `bcryptjs` с `cost=10`.
- **IPC-изоляция** — `contextIsolation: true`, `nodeIntegration: false`,
  `sandbox: false` (необходимо для better-sqlite3 в main, но renderer
  изолирован).
- **CSP** — задана в `index.html`, ограничивает источники скриптов и стилей.
- **Внешние ссылки** — открываются через `shell.openExternal`, не в окне
  приложения.

### 5.3. Ключевые модули

- `src/main/db/migrations.ts` — DDL базы данных, выполняется при первом запуске.
- `src/main/db/seed.ts` — наполнение тестовыми пользователями и шаблонами.

  слой репозитория для UI.

## 7. Заключение

Разработана desktop-СЭД для промышленного предприятия со всеми ключевыми
функциями: шаблоны, маршруты согласования, журнал, экспорт. Решение полностью
автономно, не требует серверной инфраструктуры и легко переносится между
рабочими станциями (один SQLite-файл).

Возможные направления развития:

- Многопользовательский режим (синхронизация SQLite через WebDAV/Dropbox или переход на серверную БД).
- Параллельные маршруты согласования.
- Шаблоны DOCX с подстановкой через `docxtpl`.
- Электронная подпись (ГОСТ Р 34.10-2012, КриптоПро CSP).
- Интеграция с Active Directory.
